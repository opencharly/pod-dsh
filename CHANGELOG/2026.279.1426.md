# 2026.279.1426 — fix(dsh-web): wire --trusted-host + document the two-layer web auth and the 1:1 proxy mapping

## Summary

`dsh web` authenticates at **two independent layers**, and the `dsh-web` candy
documented only the first — a blind spot that makes a reverse-proxy-exposed
deployment load a dead page:

1. **The launch token** — each process mints a random token and prints it in its
   `dsh web: http://127.0.0.1:3080/?token=…` readiness line. `GET /?token=…` (root
   only) answers `303` and sets a signed, authority-bound cookie. Missing or
   wrong-authority cookie → **401**.
2. **The Host / Origin browser-trust fence** (`dsh-client-connection`'s
   `api-request-trust`) — every API/WebSocket request passes it **before**
   authentication. The request `Host` must be loopback **or** match a
   `trustedHosts` entry. Failed Host → **403 forbidden**; trusted but
   unauthenticated → **401 unauthorized**.

Because `dsh web` binds loopback-only, every off-loopback route is a reverse proxy
(`tailscale serve`, an SSH `-L` tunnel), and a proxy forwards
`Host: <proxy-authority>` — neither loopback nor trusted by default. The shell
loads (`/` → 200) while **every `/api/*` call returns 403** and the SPA renders an
"authentication required" page. A probe that checks only `GET /` passes while the
browser UI is broken — which is exactly what the shipped candy did.

This change makes the deployment configurable and the regression visible:

- **`candy/dsh-web/dsh-entrypoint`** — forward `DSH_WEB_TRUSTED_HOSTS` (space- or
  comma-separated `host:port`) as one repeatable `--trusted-host` per entry. Unset
  = loopback-only, correct for the default in-pod case.
- **`candy/dsh-web/charly.yml`** — declare the env var and document both layers.
- **`charly.yml` (`/charly-tools:dsh` skill)** — the two layers, the
  reverse-proxy recipe with a **1:1** `tailscale serve --https=3080` mapping (dsh
  does not occupy 443), and the rule "`GET /` 200 is not proof — exercise `/api/*`".
- **`charly.yml` (`check-dsh-pod`)** — two assertions: the fence **rejects** a
  forged non-loopback `Host` on `/api/*` (**403**), and the entrypoint **forwards**
  each `DSH_WEB_TRUSTED_HOSTS` entry as a repeatable `--trusted-host`.
- **`charly.yml` (`/charly-tools:dsh-tui` skill)** — the terminal-channel driving
  contract (unique run-ids; `transcript` not `snapshot`; `close` is not a reap; the
  interactive-submit race is asserted separately with a one-shot headless call).
- **`README.md`** — correct the same single-layer claim (R5 sweep below).

Closes #12.

### RCA — a self-inflicted failure the first check version caused (R1)

The first version of the forwarding check overrode `HOME` but not `DSH_HOME`,
which the `dsh-web` candy sets in the container environment. The entrypoint
therefore still resolved `DSH_HOME` to the **live** `~/.dsh`, ran its
`rm -f $DSH_HOME/web-token` against the real service, and left the running web UI
tokenless — 401-ing the two downstream checks. Measured signature:

```
  FAIL  check the dsh web-running verb probes the web UI in-box  [dsh-verb-web-running]  dsh: web-running: exit=1 ... 401
  FAIL  check the compiled-in charly dsh status command reaches the deployed box  [dsh-cmd-status]  exit=22 ... 401
```

Both read **401** (not 403), which is what names the cause as the token, not the
fence. `04c14be` overrides `DSH_HOME="$D/.dsh"` so the run is confined to the temp
dir, and the next full R10 is green (above).
