# 2026.281.0924 — chore(dsh-web): re-vendor dsh-github from its merged main (resolveRepo + browser-bundle fixes)

## Summary

Re-vendor `dsh-github` in the `dsh-web` web profile. The vendored
`perrylink-dsh-github-0.7.19.tgz` was packed from the fork's `fix/client-bundle` branch
**before** two fixes merged to `opencharly/dsh-github` main, so the container shipped a
`dsh-github` whose repo auto-resolution was inert in a `dsh web` deployment.

Re-vendored from the merged fork main `69987edd634f333f4b52ee3896dd07624662fdb8`, which
carries **both** merged PRs:

- **#6** (squash `cf92c84`) — `resolveRepo`'s git-origin fallback now anchors on the
  calling **session's** cwd (`agent.session.header.cwd`), and `repoFromRemoteUrl`
  accepts the provider host under `api.github.com`/`github.com` (a normal `github.com`
  origin used to parse to `null`, so the fallback could never fire).
- **#2** (squash `69987ed`) — `lib/client.js` ships the DSH loader bundle
  (`window.__ModuleLoader__.load({…})`, 0 raw ESM imports), so the web shell installs it
  as a classic script without throwing.

Changed paths:

  (same version/filename, so the candy `package.json` `file:` dep is unchanged).

## Why

"Fix things forward and update the version in the container": the fork advanced, so the
vendored artifact must advance with it, or the image ships a plugin the source has
already fixed. This is the same offline-`file:`-dep model the profile already uses — no
new mechanism.
