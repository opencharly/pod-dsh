## Why

A reproducible candy must not reach codeload + the npm registry for plugins whose
built artifacts are on disk. The git-dep path also **shipped `dsh-git-worktree`
unbuilt** — a git dep whose `prepare` pnpm did not run — so it silently failed to
import (`dsh: warning: 1 entry did not activate — dsh-git-worktree: failed to
import`) while still being listed. Vendoring the BUILT package fixes both.

## Provenance of the vendored tarballs (T3)

```bash
git -C <fork> checkout <pinned-commit>
( cd <fork> && npm pack )         # emits <name>-<version>.tgz
```

### The one tarball that is not byte-reproducible (measured, not assumed)

`dsh-workspace-enhancement-0.2.3.tgz` re-packs to a **different** hash each time.
The cause was measured:

- Its `prepare` runs `tsdown`, which compiles CSS Modules through `lightningcss`;
  the `cssExports` object is iterated in a **non-deterministic order**, so the
  emitted `lib/client.js` differs between rebuilds of the *same* commit (three
  consecutive `npm run build` runs produced three different `lib/client.js`
  hashes). Only `lib/client.js` differs — `lib/index.js` (plain `tsc`) is stable.
- Its embedded `core/dist/dsh-core-0.2.2-linux-x64.tar.gz` carries a **Go
  binary**, and Go builds are not byte-reproducible across toolchains **by the
  fork's own design** — it registers each built artifact's hash in
  `core/artifact.json` `compatHashes` instead of demanding reproducibility.

So the verifiable contract for this tarball is its **committed blob hash**
(`78d36812…`, in `SHA256SUMS`) plus the inner core hash the fork itself
provenance-gates — `1531e1099b84a444761ce813c7f8b26c2ae9647d7525ea48a1924c0f9c5c1c40`,
which is registered in the tarball's own `lib/core-artifact.js`
`CORE_COMPAT_HASHES`. The README records all of this.
